# CLI Reference

FluidCAD ships a command-line tool alongside the library. It opens FluidCAD's start screen in your browser, scaffolds a project, opens one project in your browser, writes STEP/STL/PNG files without opening the UI, and exposes the MCP server that lets AI agents drive your workspace.

FluidCAD is installed per-project, so the CLI is run through `npx` from inside the project:

```bash
npm i fluidcad
npx fluidcad --help
```

The start screen, `npx fluidcad` on its own, is the exception: it runs from any
folder, and the projects it opens need no `npm i` of their own.

:::note
A global install (`npm install -g fluidcad`) is not supported — the engine and your editor's type hints both resolve from the project's `node_modules`. If you see `Cannot find module 'fluidcad' imported from …`, run `npm i fluidcad` inside the project.
:::

| Command | What it does |
|---------|--------------|
| [`fluidcad`](#fluidcad) | Open the start screen in the browser: your projects, new projects, and the engine each one runs on |
| [`fluidcad init`](#fluidcad-init) | Scaffold a new project in the current directory |
| [`fluidcad serve`](#fluidcad-serve) | Open one project in the browser and watch its workspace |
| [`fluidcad export step`](#fluidcad-export-step) | Write a STEP file |
| [`fluidcad export stl`](#fluidcad-export-stl) | Write an STL mesh |
| [`fluidcad export png`](#fluidcad-export-png) | Capture a PNG of the viewport |
| [`fluidcad package init`](#fluidcad-package-init) | Make this project a package: write the `package` block of `fluidcad.json` |
| [`fluidcad version`](#fluidcad-version) | Raise the package's version |
| [`fluidcad pack`](#fluidcad-pack) | Pack the package into a `.fluidpkg` file to look at, without publishing it |
| [`fluidcad install`](#fluidcad-install) | Install a package from the hub, or every package this project uses that isn't installed |
| [`fluidcad remove`](#fluidcad-remove) | Remove an installed package from your library or from this project |
| [`fluidcad packages`](#fluidcad-packages) | List your library, and in a project its copies and the packages it uses |
| [`fluidcad mcp`](#fluidcad-mcp) | Run the MCP server over stdio |

Every command accepts `--help`, and `npx fluidcad --version` prints the installed version.

## `fluidcad`

```bash
npx fluidcad
```

Opens FluidCAD's start screen in your browser: the same one the desktop app
shows, with your recent projects, **New Project** and **Open Project**, and the
engine each project runs on. It is the one command you can run from anywhere;
it is not tied to a project folder. (`npx fluidcad start` is the same command
by its name.)

Every project opens in a tab of its own, and the start screen stays in its tab.
Opening a project that is already open brings its tab forward. **New Project**
asks where the project should live and what to call it, creates the folder, and
sets the project up in it, the same scaffold as [`fluidcad init`](#fluidcad-init).
Close a project from the **⋯** menu on its card; FluidCAD refuses while its tab
has unsaved changes.

Each project runs on the engine its `fluidcad.json` pins, the way the desktop
app runs it: a pin that is not on your machine is downloaded once and kept in
`~/.fluidcad/engines`, and an unpinned project is pinned to the version of
`fluidcad` you ran. The start screen and the desktop app share the recent
projects, the previews and the downloaded engines, so a project opened in one
is on the other's list too. See [Project
configuration](/docs/project-configuration#engine).

Leave the command running while you work. `Ctrl+C` stops FluidCAD and every
project it opened. Running `npx fluidcad` again while it runs opens the running
one in a new tab instead of starting a second.

| Flag | Description | Default |
|------|-------------|---------|
| `-p, --port <port>` | Port for the start screen — if it's taken, the first free port above it is used | `3100` |
| `--no-open` | Don't launch a browser, only print the start screen's link | _opens by default_ |
| `--projects <dir>` | Keep every project in this folder (see below) | _projects live anywhere_ |
| `--host <address>` | The address to listen on; `0.0.0.0` lets other machines reach FluidCAD (see below) | `127.0.0.1` |
| `--public-url <url>` | The origin browsers reach FluidCAD at behind a reverse proxy, such as `https://cad.example.com`. Also `FLUIDCAD_PUBLIC_URL` | _none_ |
| `--no-auth` | No sign-in link: anyone who reaches the start screen can use it (see below). Also `FLUIDCAD_NO_AUTH=1` | _sign-in link_ |
| `--allowed-host <name>` | A host name browsers reach FluidCAD by; any other is refused. Repeatable, or `FLUIDCAD_ALLOWED_HOSTS=a,b` | _any, when bound beyond loopback_ |

The link it prints carries a key for the session, so that no other page or user
on your machine can drive FluidCAD through it. Open it yourself when the
browser does not open on its own (over SSH, say), and don't share it.

Every project's page is served by the start server itself, at `/p/<name>/`,
which stands in for the project's engine: the engine runs on this machine's
loopback address only, and the start server forwards its page, its calls and
its live connection to it. That is what lets a browser on another machine work
on a project, below.

### A projects folder

```bash
npx fluidcad --projects ~/cad
```

With `--projects`, one folder holds every project. The start screen lists the
projects in it, all of them rather than the recent ones. **New Project** asks
only for a name, creates `<dir>/<name>` and sets the project up there. **Open
Project** is not offered, since every project in the folder is already on the
screen, and nothing outside the folder can be opened: the start server refuses
any path that is not a project in it, which is what makes the folder the
boundary when the start screen is reached from another machine. The folder has
to exist.

### Reaching FluidCAD from other machines

```bash
npx fluidcad --projects /srv/cad --host 0.0.0.0 --no-open
```

`--host 0.0.0.0` binds the start screen to every address of the machine, so a
browser on another machine (or in a container's network) can open it, and open
projects in it: each project's page goes through the start server, at
`/p/<name>/`, and the engines themselves stay on loopback where nothing else
can reach them. Pair it with `--projects`, so that the machine's other folders
stay out of reach.

What keeps it yours:

- The link `npx fluidcad` prints carries the session's key. Anyone who has it
  can use FluidCAD as you, and can read and change every project it opens, so
  keep it private. Without it a browser gets a page saying where the link is.
- The key becomes an `HttpOnly`, `SameSite=Strict` cookie, and every call
  that changes something has to come from FluidCAD's own pages.
- Nothing is encrypted by FluidCAD itself. Before leaving a private network,
  put an HTTPS reverse proxy in front of it (Caddy, nginx, Tailscale Serve,
  Cloudflare Tunnel), forwarding WebSocket upgrades too, and tell FluidCAD the
  origin it is reached at:

```bash
npx fluidcad --projects /srv/cad --host 127.0.0.1 --public-url https://cad.example.com --no-open
```

With `--public-url`, the link it prints uses that origin, calls from pages at
that origin are accepted, and, when it is `https://`, the session cookie is
marked `Secure` so it is never sent in the clear. Bound to `127.0.0.1` behind
the proxy on the same machine, the start server is not reachable any other
way.

One start server is one session, for one person or a group who share the
link. It has no accounts of its own.

### Without a sign-in link

```bash
npx fluidcad --projects /srv/cad --host 0.0.0.0 --no-auth --allowed-host cad-server --no-open
```

On a network you trust, `--no-auth` drops the link and its cookie: `http://cad-server:3100` opens the
start screen on any device, every time. Anyone who can reach it can read and
change every project, and run code on the machine through them, so never
use it on a server the internet can reach.

Bound beyond loopback, `--no-auth` needs `--allowed-host` for every name the
start screen is reached by (`cad-server`, `192.0.2.20`, a Tailscale name),
and refuses to start without one. A request under any other name is turned
away, which keeps out a hostile web page that points its own name at your
machine: without the cookie, its Host is what gives it away. The
`--public-url` name is always allowed. Calls that change something still have
to come from FluidCAD's own pages.

`--allowed-host` also works with the link, to refuse every other name.

## `fluidcad init`

```bash
npx fluidcad init
```

Scaffolds a project in the **current directory**:

```
my-app/
├── init.js             ← required project entry point
├── part1.part.js       ← an empty part to start modeling in
├── jsconfig.json       ← enables editor type hints
└── fluidcad.json       ← project configuration: engine pin, unit
```

`init.js` is required — the viewer cannot run a `.part.js` file without it. Don't edit it.

The command refuses to run if `init.js` already exists, so it can't clobber a project. `part1.part.js`, `jsconfig.json` and `fluidcad.json` are only written when they're missing, so re-running it in a half-set-up folder fills in the gaps.

| Flag | Description | Default |
|------|-------------|---------|
| `--unit <unit>` | Project length unit written to `fluidcad.json`: `mm`, `cm`, `m`, `in` or `ft` | the unit for new projects from the Settings dialog, `mm` unless changed |

```bash
npx fluidcad init --unit in        # an inch project
```

Without the flag, the unit comes from **Settings ▸ Units ▸ Unit for new projects** in the FluidCAD UI (the gear in the top bar). The desktop app's New Project uses the same setting.

See [Project configuration](/docs/project-configuration) for what `fluidcad.json` holds.

## `fluidcad serve`

```bash
npx fluidcad serve
```

Opens FluidCAD in your browser: the 3D viewport, every interactive modelling
tool, and a code editor. It renders the model you had open last (or the first
`.fluid.js` it finds in a new project) and watches the workspace, so an edit
made anywhere — the in-page editor, your own editor, an AI agent through MCP —
rebuilds the model. Press `Ctrl+C` to stop.

Where [`fluidcad`](#fluidcad) opens the start screen, `serve` opens one
project, runs it on the `fluidcad` it was installed with, and suits CI and
scripts. It also pairs with your own editor: see
[Editor setup](/docs/installation#editor-setup).

| Flag | Description | Default |
|------|-------------|---------|
| `-w, --workspace <path>` | Path to your project | Current directory |
| `-p, --port <port>` | Server port — if it's taken, the first free port above it is used | `3100` |
| `--no-open` | Don't launch a browser — for CI and remote sessions | _opens by default_ |

```bash
npx fluidcad serve                     # open FluidCAD in your browser
npx fluidcad serve --no-open           # start the server only (CI, SSH)
npx fluidcad serve -w ./my-app         # serve a project in another directory
npx fluidcad serve -p 4000             # start at port 4000 (4001, 4002, … if busy)
```

The startup banner names the engine version that is actually running, so a
project whose `fluidcad.json` pin disagrees with it says so before anything is
rebuilt.

:::note
The code editor is hidden until you open it, from the ☰ menu or with
<kbd>Ctrl</kbd>+<kbd>B</kbd>. It docks to the left and takes width from the
scene rather than covering it, so the model stays fully visible.
:::

## `fluidcad export`

```bash
npx fluidcad export step                          # every shape → <entry>.step
npx fluidcad export stl --resolution fine -o parts/bracket.stl
npx fluidcad export png --view front --open
```

Writes a STEP, STL, or PNG file straight from the terminal — the same exports the [Export dialog](/docs/import-export/export) produces, without opening the UI.

### How the model gets rendered

The CLI works in one of two modes, chosen automatically:

- **Attached** — a FluidCAD server is already running for the workspace (started by `fluidcad serve` or an editor extension). The CLI finds it through `.fluidcad/instance.json` and exports **the scene that server is currently showing**. Nothing is re-rendered, and no second server is started.
- **Ephemeral** — nothing is running. The CLI forks its own server on a free port, renders your entry file, exports, and shuts the server down again.

Because an attached server's scene wins, passing `--entry` while one is running only prints a warning — what the server shows is what gets exported. Stop the server to export a different file.

### Common flags

These apply to all three formats:

| Flag | Description | Default |
|------|-------------|---------|
| `-w, --workspace <path>` | Path to your project | Current directory |
| `-e, --entry <file>` | Which `.fluid.js` to render | The workspace's only one |
| `-o, --out <path>` | Output file | `<entry>.<ext>` in the current directory |
| `-p, --port <port>` | Export from the running server on this port instead of discovering one | Auto-discovered |
| `--timeout <sec>` | Seconds to wait for the server (and, for `png`, for a browser) | `60` |

If the workspace holds more than one `.fluid.js` file, `--entry` is required — the CLI won't guess.

### `fluidcad export step`

| Flag | Description | Default |
|------|-------------|---------|
| `--shapes <ids...>` | Export a subset of the scene's shapes | Every solid (an assembly: the [whole assembly](#assemblies)) |
| `--list-shapes` | Print the scene's shapes and exit without exporting | — |
| `--no-colors` | Write plain geometry instead of per-shape colors | _colors on_ |
| `--configuration <name>` | Export this [configuration](/docs/part/configurations) (`Default` for the `param()` literals) | The one on screen |
| `--all-configurations` | Write one file per configuration: `<model>.step` for Default, `<model>-<Row>.step` per row | — |

```bash
npx fluidcad export step --no-colors -o build/housing.step
```

### `fluidcad export stl`

| Flag | Description | Default |
|------|-------------|---------|
| `--shapes <ids...>` | Export a subset of the scene's shapes | Every solid (an assembly: the [whole assembly](#assemblies)) |
| `--list-shapes` | Print the scene's shapes and exit without exporting | — |
| `--resolution <r>` | Mesh resolution: `coarse`, `medium`, `fine`, or `custom` | `medium` |
| `--linear-deflection <length>` | Custom linear deflection, in document units | — |
| `--angular-deflection <deg>` | Custom angular deflection, in degrees | — |
| `--scale-to <mm\|document>` | Write the STL in millimetres (what slicers expect) or keep the document's unit | `mm` |
| `--configuration <name>` | Export this [configuration](/docs/part/configurations) (`Default` for the `param()` literals) | The one on screen |
| `--all-configurations` | Write one file per configuration: `<model>.stl` for Default, `<model>-<Row>.stl` per row | — |

The two deflection flags imply `--resolution custom`, and `custom` needs both of them:

```bash
npx fluidcad export stl --linear-deflection 0.01 --angular-deflection 0.1
```

Passing a deflection alongside `--resolution fine` is an error rather than a silent override.

### Picking shapes

`--list-shapes` prints what the scene contains, numbered:

```
3 shapes:
  1  a1f2…  SOLID  Extrude
  2  b7c4…  SOLID  Fillet
  3  c9e0…  SOLID  Housing
```

`--shapes` then takes any mix of:

- a **position** from that listing — `--shapes 1 2`
- a **feature name** — `--shapes Housing` (case-insensitive; exports every shape that feature produced)
- a **shape id** — `--shapes a1f2…`

Positions and names survive a re-render; **shape ids are minted fresh every time the model rebuilds**, so don't hard-code them in a script.

```bash
npx fluidcad export step --list-shapes
npx fluidcad export step --shapes 1,3 -o build/plates.step
npx fluidcad export stl --shapes Housing --resolution fine
```

### Assemblies

When the scene is a `*.assembly.js` file, `export step` and `export stl` write the **whole assembly** by default: every inserted part where it sits. STEP keeps the structure — one product per part, one component per instance, sub-assemblies nested — so it opens as an assembly tree elsewhere. STL flattens every placed part into one mesh.

```bash
npx fluidcad export step                 # robot.assembly.js → robot.step, the full tree
npx fluidcad export stl --resolution fine
npx fluidcad export step --shapes 1      # a single part template instead, in its own frame
```

Mates are solved in the viewer, and the CLI has no viewer, so parts land where the source places them (`insert().translate()` / `.rotate()`). The CLI prints a note when that is the case; for the mated layout, export from the viewer's Export menu.

### Configurations

A model with a `configurations()` table ([parts](/docs/part/configurations), [assemblies](/docs/assembly/configurations)) exports the configuration on screen unless `--configuration` names another; the configuration on screen is left as it is. Without `--shapes`, a part file exports every solid that configuration builds, so a row that adds or leaves out a body exports exactly its own bodies. With `--shapes`, each listed solid is found in the configuration by its history, and one the configuration does not build fails the export with a message naming it. `--all-configurations` writes one file per configuration, with row names made file-safe (anything but letters, digits, `.`, `_` and `-` becomes `-`); with `-o`, that path minus its extension is the base name:

```bash
npx fluidcad export step --configuration Wide              # frame.step, the Wide row
npx fluidcad export step --all-configurations              # frame.step, frame-Compact.step, frame-Wide.step
npx fluidcad export stl --all-configurations -o build/frame.stl
```

`--all-configurations` renders every configuration before writing anything: if one fails, no file is written. Pass one flag or the other, not both. `--all-configurations` is not available for `png`, which captures one image. In a STEP file, an instance inserted with a configuration carries it in its name: `frame (Wide)`.

### `fluidcad export png`

| Flag | Description | Default |
|------|-------------|---------|
| `--width <px>` | Image width | `800` |
| `--height <px>` | Image height | `800` |
| `--view <name>` | Camera view (see below) | `iso-ftr` |
| `--margin <px>` | Crop/fit margin | `20` |
| `--transparent` | Transparent background | _off_ |
| `--show-axes` | Show the origin axes | _off_ |
| `--no-grid` | Hide the ground grid | _grid shown_ |
| `--no-auto-crop` | Keep the full frame instead of cropping to the model | _crop on_ |
| `--no-fit` | Don't fit the camera to the model | _fit on_ |
| `--open` | Open the viewport in a browser to render the capture | _off_ |
| `--configuration <name>` | Capture this [configuration](/docs/part/configurations): the viewer shows it for the capture, then switches back | The one on screen |

`--view` takes `current` (whatever the connected browser is looking at) or a named view:

| | |
|---|---|
| Orthographic | `front`, `back`, `left`, `right`, `top`, `bottom` |
| Isometric | `iso-ftr`, `iso-fbr`, `iso-ftl`, `iso-fbl`, `iso-btr`, `iso-bbr`, `iso-btl`, `iso-bbl` |

Isometric names read as _front/back_, _top/bottom_, _left/right_ — `iso-fbl` is the front-bottom-left corner.

```bash
npx fluidcad export png --view top --width 1600 --height 1200
npx fluidcad export png --transparent --no-grid -o docs/hero.png
```

:::warning
**PNG capture needs a browser.** Screenshots are rendered by the FluidCAD viewport itself, so a browser has to be connected to the server. Pass `--open` and the CLI launches one and waits for it; otherwise open the server URL yourself before the `--timeout` runs out.

If a server is already attached and no browser is on it, the command fails immediately and tells you the URL to open — re-run with `--open`, or stop that server so the CLI can spawn its own.
:::

## Packages

A [package](/docs/packages) is a project's custom features and parts, which `fluidcad publish` packs into one `.fluidpkg` file and uploads to the hub, from which other projects install it. These commands make one, install one from the hub, and list what is installed. A `.fluidpkg` file itself never installs. Packages are installed into your library, the home directory's `~/.fluidcad/packages` unless **Settings ▸ Packages ▸ Library folder** names another folder (the `FLUIDCAD_PACKAGES` environment variable overrides both), or into a project's own `packages/` folder.

### `fluidcad package init`

```bash
npx fluidcad package init --name @acme/mounting-hardware
```

Makes the project a package by writing the [`package` block](/docs/project-configuration#package) of its `fluidcad.json`: the name and version `0.1.0`. The name is `@<your hub handle>/<name>` ([Package names](/docs/packages#package-names)). Signed in to the hub (`npx fluidcad login`), a name without the scope takes your handle, and the command says so; signed out, it is refused with `"name" "mounting-hardware" needs your hub handle as its scope: write "@<your-handle>/mounting-hardware"`. What the package shares is what its `features/`, `parts/` and `assemblies/` folders hold, and the command says how much that is today:

```
Named it @acme/mounting-hardware: your handle on https://hub.fluidcad.io.
Wrote the "package" block to …/mounting-hardware/fluidcad.json:
  {
    "name": "@acme/mounting-hardware",
    "version": "0.1.0"
  }
The package exports what features/, parts/ and assemblies/ hold. Today: features/ 4 modules, parts/ 2 modules, assemblies/ none.
```

| Flag | Description | Default |
|------|-------------|---------|
| `-n, --name <@handle/name>` | The package name, each part in lowercase letters, digits and single dashes, starting with a letter. Signed in, a name without the scope takes your handle | asked for in a terminal |
| `--hub <url>` | The hub whose handle scopes a name without one | `FLUIDCAD_HUB_URL`, else `https://hub.fluidcad.io` |
| `-w, --workspace <path>` | Path to the project | Current directory |

Asked in a terminal, the prompt shows your handle when you are signed in (`Package name: @acme/`); a name typed with a scope is taken as typed.

It refuses a project that already has a `package` block, and a `fluidcad.json` it cannot read.

### `fluidcad version`

```bash
npx fluidcad version minor
```

Raises the package's version in `fluidcad.json`: `major`, `minor` or `patch`, or an exact version such as `1.2.0`. It prints the change, `@acme/mounting-hardware 0.1.0 → 0.2.0`, and refuses the version the package already has. `-w, --workspace <path>` points it at another project.

### `fluidcad pack`

```bash
npx fluidcad pack
npx fluidcad pack -o dist/
```

Packs the project's package into `<scope>-<name>-<version>.fluidpkg`, written into the project unless `-o` says otherwise, so you can look at what would be published (its files and its `manifest.json`) without publishing. Publishing doesn't need it: `fluidcad publish` packs the project the same way, with the same checks, and uploads that. The file doesn't install anywhere. It lists what the package holds, folder by folder:

```
Packed @acme/mounting-hardware 0.1.0 → …/acme-mounting-hardware-0.1.0.fluidpkg
  features/   4 features: boltCircle, boss, fastener, standoff
  parts/      2 parts: hubFlange, pcbPlate
  assemblies/ 1 assembly: plateStack
  29 files, 18.2 kB, unit mm
```

| Flag | Description | Default |
|------|-------------|---------|
| `-o, --out <path>` | The output file, or a folder to write it into | `<scope>-<name>-<version>.fluidpkg` in the project |
| `-w, --workspace <path>` | Path to the project | Current directory |
| `--json` | Print the result as JSON: `name`, `version`, `fileName`, `savedTo`, `bytes`, `files`, `unit`, and `contents` (the features, parts and assemblies by folder, with `models`, their count). A refused pack prints `{ "error", "code" }`. | off |

The file holds what the [`features/`, `parts/` and `assemblies/` folders](/docs/packages#making-a-package) hold, the files they import and the pictures their features declare, unchanged, plus `README.md`, `LICENSE` and `CHANGELOG.md` when the project has them, and three generated files: `index.js`, `manifest.json` (what the package holds, read by the installer) and a `fluidcad.json` with only the unit and materials. Test models outside the folders, `init.js` and anything else not imported stay out, and nothing else is written to the project. The same project packs to the same bytes every time. A package with no part or assembly packs, and the summary notes that the hub needs at least one to publish it.

Before writing, the engine loads every file the folders export, builds every part and assembly with its default values and checks every feature. A problem stops the pack with one sentence naming the file, for example:

```
features/hub-flange.part.js is a part in features/, but parts belong in parts/: move it there.
```

The checks: the `package` block is valid (its name has your handle as its scope) and has no `exports` list; every file sits in the folder for its kind (`wrong-folder`) and the folders hold something (`no-exports`); nothing is imported from outside the three folders (`outside-layout`); no two files export the same name and no two features share an id; every part and assembly builds without an error; nothing is imported from `node_modules`, from outside the project, from `init.js`, from a blocked Node built-in or from another package; every picture a feature declares exists. A project without a `package` block is refused with "This workspace isn't a package — run `fluidcad package init` first."

To release a new version: edit, `npx fluidcad version minor`, `npx fluidcad publish`.

### `fluidcad install`

```bash
npx fluidcad install @acme/mounting-hardware          # the hub's latest version
npx fluidcad install @acme/mounting-hardware@0.1.0    # an exact version
npx fluidcad install                                  # every package this project uses that isn't installed
```

Packages install from the hub. FluidCAD downloads the package, checks that its files hash to what the hub lists (and, in a project, to the project's recorded hash), and installs it, without asking. Each package is one line: what happened, what the package holds and whether it was recorded in the project:

```
✓ Installed @acme/mounting-hardware@0.1.0 into your library · 4 features, 2 parts · pinned in fluidcad.json
```

A warning that matters gets a short line under it: a deprecated package, a yanked or unpublished version you asked for by its exact version, an older version because the latest needs a newer FluidCAD. A package that can't be installed (unknown, nothing published, a hash that doesn't match, removed by the hub's admins) prints why and the command exits with status 1. A package's code runs in the FluidCAD engine with your permissions: install only packages you trust.

**A name alone** asks the hub for its latest version this FluidCAD runs, and uses your library's copy of that version when its files are the hub's. When the hub can't be reached, it uses the newest version your library holds, and says so. **A name with `@version`** takes your library's copy (or this project's) when there is one, else downloads it. A name without the scope (`npx fluidcad install mounting-hardware`) is refused with "Name the publisher: `fluidcad install @<handle>/mounting-hardware`."

Run inside a project, it records the package in the project's [`dependencies`](/docs/project-configuration#dependencies) (with `--project`, it also copies a library package into the project's `packages/` folder); run elsewhere, it only installs. Installing the same version with the same contents again changes nothing. The same version with other contents is refused unless `--replace` is given, and in a project whose recorded hash differs, it is refused either way.

**With no arguments**, in a project, it downloads every package the project records but this machine doesn't have, each at its recorded version and checked against its recorded hash, with a line per package. A package that can't be installed is listed and the command exits with status 1.

A `.fluidpkg` file, or any other path, is refused: "Packages install from the hub: `fluidcad install @<handle>/<name>`. A .fluidpkg file is an archive to look inside (`fluidcad pack` writes one); it isn't installed."

| Flag | Description | Default |
|------|-------------|---------|
| `--library` | Install into your library | _the **New packages go to** setting, the library unless changed_ |
| `--project` | Install into this project's `packages/` folder; with a package already in your library, copy it there | _off_ |
| `--replace` | Replace an installed copy of the same version whose contents differ | _off_ |
| `--hub <url>` | The hub to download from | _`FLUIDCAD_HUB_URL`, else `https://hub.fluidcad.io`_ |

### `fluidcad remove`

```bash
npx fluidcad remove @acme/mounting-hardware              # from your library
npx fluidcad remove @acme/mounting-hardware --project    # this project's copy
npx fluidcad remove @acme/mounting-hardware@0.1.0        # one of several installed versions
```

Removes an installed package's files. It never changes a project's `dependencies`: a project that still uses the package says so and asks for it on its next render.

```
Removed @acme/mounting-hardware 0.1.0 from your library (/Users/you/.fluidcad/packages).
This project still pins @acme/mounting-hardware 0.1.0, which is no longer installed: its models will ask for it until you install it again (fluidcad install).
```

| Flag | Description | Default |
|------|-------------|---------|
| `--library` | Remove it from your library | _the default_ |
| `--project` | Remove it from this project's `packages/` folder | _off_ |

### `fluidcad packages`

```bash
npx fluidcad packages
```

Lists your library and, in a project, the project's own copies and the packages it uses, with where each one loads from:

```
Your library: /Users/you/.fluidcad/packages
  @acme/mounting-hardware 0.1.0  4 features, 2 parts, 41.4 kB
This project's packages folder: /Users/you/cad/controller-enclosure/packages
  (empty)
Pinned in fluidcad.json:
  @acme/mounting-hardware 0.1.0  from your library
```

## `fluidcad mcp`

```bash
npx fluidcad mcp
```

Runs the FluidCAD [MCP](https://modelcontextprotocol.io) server over stdio, so an LLM agent can drive your workspace: take screenshots, inspect geometry, measure, edit source, and look up the API. It's bundled with the `fluidcad` package — there's nothing extra to install.

You don't normally run this by hand; you register it with an MCP client.

**Claude Code** — register at user scope so it's available in every project:

```bash
claude mcp add --scope user FluidCAD -- npx -y fluidcad mcp
```

**Claude Desktop / Cursor** — add to `claude_desktop_config.json` or `~/.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "FluidCAD": {
      "command": "npx",
      "args": ["-y", "fluidcad", "mcp"]
    }
  }
}
```

**opencode** — run `opencode mcp add`, or add to `~/.config/opencode/opencode.json`:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "FluidCAD": {
      "type": "local",
      "command": ["npx", "-y", "fluidcad", "mcp"],
      "enabled": true
    }
  }
}
```

The server serves the companion FluidCAD skills to the agent itself, at the version matching the server: it implements the MCP Skills Extension (SEP-2640), so hosts that support it list `skill://fluidcad/SKILL.md` and its siblings next to local skills, and every other client gets them through the `list_skills` / `read_skill` tools, which the startup instructions point at before modeling. Clients with native skill support can additionally install them for automatic triggering:

```bash
npx skills add Fluid-CAD/FluidCAD
```

An installed copy is frozen at install time, so re-run that after upgrading `fluidcad`.

The agent drives a **running** workspace, so start one first — with `fluidcad serve` or an editor extension — and the MCP server attaches to it.

See the [MCP README](https://github.com/Fluid-CAD/FluidCAD/blob/main/mcp/README.md) for the full tool surface and transport details.
