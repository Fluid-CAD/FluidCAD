# Custom Features

A custom feature is a feature type your project defines: a PCB standoff, a bolt circle, a vent grid. It lives in a `*.feature.js` file in the project, and from then on it works like a built-in feature: the toolbar offers it with its own dialog and preview, Apply writes the statement, its History row opens the dialog again, and models call it in code. Write one when a construction of several steps recurs with different values and should be one statement and one row.

For geometry that occurs once, write the statements in the model; for the same geometry again in one model, use [Repeat or Copy](/docs/patterns/repeat); for a whole part reused with other dimensions, use a [part with parameters](/docs/part/param).

## In the viewport

1. Click **Custom**, the last button on the part toolbar. It lists every custom feature of the project, with its icon.

   ![The Custom dropdown](/img/docs/ui/custom-features-menu.png)

2. Click a feature. Its dialog opens docked on the right, built from the values the feature declares: here **On face** (click a face in the viewport), **Height**, **Boss diameter** and **Hole diameter**, with the **Add / New** tabs and a **Scope** slot.
3. Turn on **Preview** to see the result as a ghost, green for what the feature adds and red for what it cuts. The toggle starts off and stays on once you turn it on for a feature.
4. Click **Apply**. The statement and its import are written into the file, and the History panel gains a row with the feature's name.

Double-click the row to edit the feature: the dialog opens with the statement's values (**Edit standoff**), and Apply rewrites the statement.

![Editing a standoff, with its preview](/img/docs/ui/custom-feature-edit.png)

The written call is plain code, and later features use the feature's faces like any other: below, a fillet on the standoff's top edges and a repeat of the pad, the standoff and the fillet at the plate's four corners.

## Writing a feature

A feature file holds a class and the builder it exports:

1. The class extends `Feature.with({ … })`, which declares the feature's values: each one is typed in (`{ type: 'length', default: 10 }`) or picked in the viewport (`{ picker: 'face' }`).
2. `static id` is the feature's type, a plain name: `'standoff'`. It can't be one of FluidCAD's own types (`extrude`, `fillet`, `part`, …). Installed from a [package](/docs/packages), the feature is told apart by the package it comes from, so two packages' `standoff` never clash.
3. `buildTool()` builds the solid the feature adds or cuts, where its picked face stands. FluidCAD applies the operation (add, new or remove) and fuses or cuts the result. `setBuckets()` names its faces, so that `post.endEdges()` in a model reaches its top rims. A feature can also give names of its own to what it makes: see [Faces and edges with names of their own](#faces-and-edges-with-names-of-their-own).
4. `defineFeature(Class, { … })` describes the feature for the toolbar and the dialog (label, group, the operations it offers, the call a model writes) and returns the builder. Export it by name.

An `icon: './standoff.svg'` in the description gives the feature its picture in the Custom dropdown, from an image next to the file.

### How FluidCAD finds it

- Every `*.feature.js` file in the project (outside `node_modules`, dot folders and gitignored paths) is scanned, and every **named** export that is a feature builder is offered in the Custom dropdown. Nothing is registered in `init.js`.
- A feature that can't be offered shows as a greyed entry with the reason as its tooltip: a file that fails to load, a file that exports no feature, two features with one id.
- The file is loaded again on every render, so saving it rebuilds the statements that use it, in every open model, with no restart.
- The code runs in the FluidCAD engine; the page only receives the description. Node built-ins such as `fs` or `child_process` are blocked in feature files, as in models.

### When something goes wrong

| What went wrong | Where it shows |
|---|---|
| A value in the description that FluidCAD doesn't know | The feature is greyed in the dropdown, and a model importing it fails to compile with the message. |
| A call the feature can't read (a negative height, a missing value) | The model fails to compile: `standoff(): 'height' must be at least 0, got -2`. |
| `buildTool()` throws or returns nothing | That statement's row fails with the message; the rest of the model builds. |
| `setBuckets()` gets a name the feature doesn't have, or faces of a shape `buildTool()` doesn't return | That statement's row fails: `gear: setBuckets() 'tipFace' is not a bucket of gear — did you mean tipFaces?` |

### Limits

- Custom features run in part files and part bodies, not at the top level of an assembly.
- The dialog is built from the declared values; a feature can't add its own controls.

## Faces and edges with names of their own

A feature can name parts of what it makes, so that the dialogs and a model reach them by name. The gear below names its tooth tips, flanks, roots and bore. Rounding every tooth tip is then a click and a menu choice in the viewport, and `pinion.tipEdges()` in the code.

### In a dialog

1. Click **Fillet** and click the top edge of one tooth. The statement under the dialog writes the pick through the gear's own name: `pinion.tipEdges(…)`, with a filter that picks that edge.
2. Right-click the edge. The menu leads with **Gear Tip Edges (72)**, every edge round the tips of the pinion's 18 teeth, and hovering it highlights them. The gear's other names, such as **Gear Bore Rims**, and its standard groups are under **Select other**.

   ![The right-click menu on a tooth's top edge, with Gear Tip Edges highlighted](/img/docs/ui/custom-feature-gear-menu.png)

3. Click **Gear Tip Edges**. The selection holds all 72 edges. Set **Radius** to 0.3: the statement under the dialog reads `fillet(0.3, pinion.tipEdges())`.

   ![The Fillet dialog with the gear's 72 tip edges selected](/img/docs/ui/custom-feature-gear-fillet.png)

4. Click **Apply**. Every tooth tip of the pinion is rounded. Below, the wheel's tips are rounded the same way, and its bore takes a chamfer on **Gear Bore Rims**.

   ![A gear pair on a base plate, with rounded tooth tips](/img/docs/ui/custom-feature-gear-model.png)

<ExplainedCode code={gearPair} fileName="gear-pair.part.js" />

On a repeated gear, a pick on a copy is written `r.instance(1).tipEdges(…)`.

:::note
These gears are **New** bodies. A gear added to the plate (**Add**) also counts the edges where each tip meets the plate among its tip edges, and a fillet can't round those together with the outer ones. There, keep the outer edges with a filter: `fillet(0.3, pinion.tipEdges(edge().convex()))`.
:::

### In the feature's code

The names are declared beside the values, as the second argument of `Feature.with()`, and filled in `buildTool()` with `setBuckets()`:

```js
export class Gear extends Feature.with({ /* the values */ }, {
  buckets: {
    tipFaces: {},
    tipEdges: {},
    flankFaces: {},
    rootFaces: {},
    boreFaces: {},
    boreEdges: { label: 'Bore Rims' },
  },
}) {
  // …
  this.setBuckets({ startFaces, endFaces, sideFaces, internalFaces, tipFaces, flankFaces, rootFaces, boreFaces });
```

- A name ends in `Faces` or `Edges`, which says what it holds, and becomes a method of the feature: `pinion.tipEdges()`, or `wheel.boreEdges(0)` with an index or a filter, as `endEdges()` takes them. The editor knows the names: `pinion.tipEdge()` is marked as an error.
- `label` is what the menus show after the feature's name (**Gear Bore Rims**). Without it, the menus show the name made readable (**Gear Tip Edges**).
- An edge name exists only when it is declared. `tipEdges` is declared and left out of `setBuckets()`, so it holds every edge of the tip faces.
- Say what each name holds, and in what order, in the package's `docs/` page for the feature (`docs/gear.md`). A declaration takes no description.
- A name misspelt in `setBuckets()` fails the statement's row, with the name it was probably meant to be.
- The names follow the operation. A gear added to a solid keeps what the solid still carries of each one. A feature that removes material keeps what its cut left, such as a pocket's floor. Each copy of a repeat has its own, moved with it.

## Sharing a feature

A feature file serves the project it lives in. To use it in other projects, or give it to someone, make the project a [package](/docs/packages): move the feature files into a `features/` folder (and the parts that should travel into `parts/`), run `npx fluidcad package init --name @<your handle>/<name>`, then `npx fluidcad publish` to put it on the hub. Installed elsewhere from the hub, its features appear in the Custom dropdown under the package's name.
