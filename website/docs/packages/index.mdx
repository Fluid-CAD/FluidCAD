# Packages

A package carries [custom features](/docs/custom-features) and parts from one project to others: a set of standoffs, a bolt circle, a fastener hole, a PCB plate. Packages are shared through the FluidCAD hub: you install one once into your library, and every project can use it from there. A project that uses a package records the exact version in its `fluidcad.json`, so the package's geometry never changes under the project when a newer version is installed.

This page uses `@acme/mounting-hardware`: four features (Bolt circle, Boss, Fastener hole, Standoff) and two parts (Hub flange, PCB plate).

## Package names

A package has one name, `@acme/mounting-hardware`. Its author writes it in the package's `fluidcad.json`, and it stays the same everywhere: in the packed file, on the hub, in the folder it is installed in, in the `fluidcad.json` of every project that uses it, and in every model that imports it.

- The part before the slash is the author's handle on the hub. The hub publishes a package only under its uploader's own handle, so `@acme/…` packages come from `acme`.
- Each part is lowercase letters, digits and single dashes, and starts with a letter.
- Two publishers can each have a `…/mounting-hardware`. A project can use both, because their names differ.

Feature ids are plain names (`standoff`). In a project that installs a package, each feature is told apart by the package it comes from, so `@acme/mounting-hardware`'s `standoff` never clashes with another package's `standoff` or the project's own.

## Installing a package

Packages install from the hub, from the terminal:

```bash
npx fluidcad install @acme/mounting-hardware
```

FluidCAD downloads the package, checks that its files are the ones the hub lists, and installs it, printing one line with what the package holds:

```
✓ Installed @acme/mounting-hardware@0.1.0 into your library · 4 features, 2 parts · pinned in fluidcad.json
```

It installs into your library (`--project`: into the project's `packages/` folder, committed with it; the default is the **New packages go to** setting) and, in a project, records the package in `fluidcad.json`. In a project, `npx fluidcad install` alone downloads every package the project records but this machine doesn't have. The [CLI reference](/docs/cli#fluidcad-install) has every form and flag.

A package's code runs in the FluidCAD engine with your permissions, and `fluidcad install` doesn't ask first. Install only packages you trust.

Installing the same version again with the same contents changes nothing. The same version with different contents is refused unless you add `--replace`: an installed version never changes by itself.

A `.fluidpkg` file doesn't install: it is the archive `fluidcad pack` writes so you can look inside a package. A machine that can't reach the hub uses the packages its library already holds, or a project's own copies (**Copy into project**, below). Installing from the app comes with the hub's panel in a later version.

## Using a package's features

The toolbar's **Custom** dropdown, the last button on the part toolbar, lists your project's own custom features under **This project**, then each package under its name and version. A package that is in your library but not yet used by this project is marked **not in this project**.

![The Custom dropdown with a package's features](/img/docs/ui/packages-custom-menu.png)

Click a feature to open its dialog, the same way as a project's own feature: pick the face, type the values, click **Apply**. The first time you use a feature from a package, FluidCAD records the package in `fluidcad.json` and the mark goes away. No package files are copied into the project.

<ExplainedCode code={packageTray} fileName="tray.part.js" />

The pin it writes in `fluidcad.json` is the version and a hash of the package's contents:

```json
{
  "engine": "0.0.46",
  "dependencies": {
    "@acme/mounting-hardware": {
      "version": "0.1.0",
      "integrity": "sha256-9gPApDnFu7GQz1+By40SoZnvxLgLSZDezAbqJSxF2Mw="
    }
  }
}
```

See [Project configuration](/docs/project-configuration#dependencies) for the format.

## Inserting a package's parts

A package's parts are inserted into an assembly, like the parts of your own files. In an assembly, **Insert** lists the project's parts under **This project** and each package's parts under the package's name. Click a tile, then **Insert**.

![The Insert part dialog with a package's parts](/img/docs/ui/insert-dialog-packages.png)

<ExplainedCode code={packageController} fileName="controller.assembly.js" />

A part file shows only the parts it declares. Using the package's Standoff in `tray.part.js` does not add the package's PCB plate or Hub flange to the tray; they appear only where an assembly inserts them.

A package's part is built in the package's own unit and takes its material from the package, so its size and mass are the same in every project.

## The packages of a project

The **Packages** button on the top bar opens **Packages in this project**: every package the project uses, its version, and where it loads from.

![Packages in this project](/img/docs/ui/project-packages-dialog.png)

- **Copy into project** copies the package from your library into the project's `packages/` folder. Use it for a project that must carry its packages: committed to git, zipped for a teammate, or opened on a machine that doesn't have the package. A copy in the project wins over the library.
- **Use from library** removes that copy again; the package loads from your library.

The render doesn't change in either direction: the copy and the library hold the same files, checked against the hash in `fluidcad.json`. The `packages/` folder does not show in the editor's file list.

## When a package is missing

A project whose package is not installed on this machine (a project from a teammate, or after you removed the package) does not render. The error banner names the package and the command that downloads it, and the top bar's **Packages** button carries a red dot until it is installed. **Packages in this project** shows the same command for each missing package.

![The missing-package banner](/img/docs/ui/package-missing-banner.png)

Run it, `npx fluidcad install @acme/mounting-hardware@0.1.0`, or `npx fluidcad install` for every missing package: FluidCAD downloads the version the project recorded and checks it against the project's hash, and the model renders again, without a restart. The other reasons a package can't load are listed in the same banner:

| Banner | What to do |
|--------|------------|
| `` `@acme/mounting-hardware` is not a dependency of this project — install it or add it from your library. `` | The file imports a package the project has not recorded. Use one of its features from the **Custom** dropdown, or run `npx fluidcad install @acme/mounting-hardware`. |
| `` The installed `@acme/mounting-hardware` 0.1.0 differs from the one this project was built with. `` | The installed copy is not the one the project recorded. Download the original with `npx fluidcad install @acme/mounting-hardware@0.1.0 --replace`. |
| `` `@acme/mounting-hardware` 0.1.0 needs FluidCAD 0.0.50 or newer; this engine is 0.0.46. `` | Open the project on a newer engine. |

## Installed packages are read-only

A package never changes once installed. Its files are read-only on disk, and FluidCAD refuses every edit aimed at them: a dialog, a breakpoint, a material or a connector on a package's part. A History row that comes from a package's file carries a package mark, and double-clicking it says the row is read-only. To change a package, change it in its own project, raise its version and publish it again (below).

The code editors know a package that a project records: hovering `standoff(` shows its values, completion offers them, and in VS Code and Neovim go to definition opens the package's read-only file. For VS Code and Neovim, FluidCAD keeps a small types folder at `node_modules/@types/acme__mounting-hardware`; it is rewritten when the project's packages change, and is safe to delete. Never install a package into `node_modules/@acme/mounting-hardware` yourself: FluidCAD refuses a package it finds there.

## Your library

The **Packages** tab of the settings holds your library: the packages installed on this machine.

![Settings, the Packages tab](/img/docs/ui/settings-packages-tab.png)

- **Library folder**: where the library lives. Empty uses the default, the home directory's `~/.fluidcad/packages`. In the desktop app **Browse…** picks a folder. After a change, the tab offers to copy the packages of the old folder into the new one (**Copy packages** / **Leave them**); nothing moves by itself. Projects record packages by name and version, not by folder.
- **New packages go to**: **My library** or **This project**, where an install puts a package unless told otherwise.
- **Installed in my library**: each package with its version, contents and size. The bin removes it after a confirmation: projects that use it will ask for it again.

Like every settings tab, the folder and the target wait for **Save**.

## Making a package

A package is a project whose `fluidcad.json` has a `package` block (the package's name and version) and whose features and parts sit in three folders. The folders decide what the package shares:

```
mounting-hardware/
├── fluidcad.json              ← the package block
├── README.md
├── features/                  ← *.feature.js files, with their pictures
│   ├── bolt-circle.feature.js
│   ├── bolt-circle.svg
│   ├── standoff.feature.js
│   └── standoff.svg
├── parts/                     ← *.part.js files
│   ├── hub-flange.part.js
│   └── pcb-plate.part.js
├── assemblies/                ← *.assembly.js files
│   └── plate-stack.assembly.js
└── bench.part.js              ← a test model: outside the folders, never packed
```

- Every feature in `features/`, every part in `parts/` and every assembly in `assemblies/` is shared. Subfolders are fine, and so are plain `.js` helper files inside the three folders.
- The package's own parts import its features relatively: `import { boltCircle } from '../features/bolt-circle.feature.js'`. An assembly inserts its parts the same way.
- Anything outside the three folders stays in the project: test models, `init.js`, notes. A test model at the root imports `./features/standoff.feature.js`.
- To be published on the hub, a package needs at least one part or assembly, so its page has a model to show. A package of features alone still packs, but can't be published.

### A new package

1. On the start screen, click **New Package**, beside **New Project**.
2. Type the package name, `@acme/mounting-hardware`. The part before the slash is your hub handle; the part after it names the package ([Package names](#package-names)). A name that doesn't fit is refused in the dialog, with the rule.

   ![The New package dialog of the desktop app](/img/docs/ui/new-package-dialog.png)

   The desktop app then asks where the package should live, in the same folder dialog as New Project (**Create package**): pick an empty folder. **File ▸ New Package…** opens the same name dialog. In the browser (`npx fluidcad`), the folder picker's create form has a **Project / Package** choice; **Package** adds the name field, and the folder name follows the part after the slash until you type one. **Create package** opens it.

   ![The browser's folder picker on Package](/img/docs/ui/new-package-picker.png)

3. The package opens on `parts/part1.part.js`. Its folder holds the block (version `1.0.0`), the three folders, a `README.md` with the name as its heading, and the files every project has (`init.js`, `jsconfig.json`, `.gitignore`). On the start screen its card wears a **Package** badge.

Model as in any project: write the features in `features/`, the parts in `parts/`, the assemblies in `assemblies/`, and try them in test models at the root. Only new packages are made this way; FluidCAD doesn't turn an existing project into a package.

From the terminal, [`npx fluidcad init --package @acme/mounting-hardware`](/docs/cli#fluidcad-init) writes the same folder in an empty directory. For a project that already holds the features and parts, [`npx fluidcad package init --name @acme/mounting-hardware`](/docs/cli#fluidcad-package-init) writes the block alone; move the files into the three folders yourself. Signed in to the hub (`npx fluidcad login`), both take a name without the handle and add yours; signed out, it is refused. See [Project configuration](/docs/project-configuration#package) for every key of the block.

### Publishing

In a package, the top bar's **Share** seat reads **Publish**.

![The top bar of a package, with Publish](/img/docs/ui/publish-button.png)

1. Click **Publish**. The dialog shows the package's name and version, a **New version** field (type the next version and press **Set**; there are no patch / minor / major buttons), and where the package stands on the hub. Signed out, it says so and offers **Sign in**: the hub's sign-in page opens in your browser, and the dialog comes back signed in.
2. For a version that follows a published one, type the **release notes** (at most 280 characters; left empty, the hub takes the `CHANGELOG.md` section for the version). A first version has no field: the hub asks in the next step.
3. Click **Publish** (**Check** runs the same steps against the hub without storing anything). FluidCAD packs the package with the running engine and shows the summary: what each folder holds, the number of files and the size, the archive's integrity hash, and what happens next. Nothing is sent yet.

   ![The Publish dialog's summary, with Upload and Cancel](/img/docs/ui/publish-dialog-summary.png)

4. Click **Upload**. A first version becomes a draft: the hub's publishing wizard opens in your browser, where you add screenshots, a license and release notes, and submit it; an admin reviews it before it is public. The dialog shows the draft with **Open the wizard** and **Withdraw**, and the day a draft nobody touches is deleted.

   ![The Publish dialog after a first upload: the draft row and the wizard link](/img/docs/ui/publish-dialog-draft.png)

   A later version goes straight to review, with **View its status**. A version the admins turned down shows their note and **Publish again** under the same version number. The latest published version has **Manage on the hub**.

**Withdraw** deletes the draft or the version in review from the hub, after a confirmation; its number is free again. The dialog refuses to publish while a file of the package has unsaved changes (save first), while another version of it is a draft or in review (withdraw it, or finish it on the hub), and when the version is not above the latest one on the hub (type a higher one in **New version**). A broken `package` block opens the dialog on the problem.

Before anything is uploaded, FluidCAD builds every part and assembly and checks every feature; a problem stops it with a sentence naming the file. A part file inside `features/`, an assembly inside `parts/`, or an import of a file outside the three folders stops it too. The package holds the three folders' files, the files they import and the pictures the features declare, as they are. The project's test models and `init.js` stay out.

To release a new version: edit the files, type the next version in **New version** and press **Set**, and publish again.

From the terminal, `npx fluidcad publish` runs the same steps and prints the same summary, asking before the upload (`--notes <text>`, `--dry-run`, `--status` for where the package stands, `--withdraw`); `npx fluidcad version minor` (or `patch`, `major`, or an exact `1.2.0`) raises the version. To look at what would be published without publishing anything, pack the project. Publishing never needs this: **Publish** and `npx fluidcad publish` pack on their own.

```bash
npx fluidcad pack
```

```
Packed @acme/mounting-hardware 0.1.0 → …/acme-mounting-hardware-0.1.0.fluidpkg
  features/   4 features: boltCircle, boss, fastener, standoff
  parts/      2 parts: hubFlange, pcbPlate
  assemblies/ 1 assembly: plateStack
  29 files, 18.2 kB, unit mm
```

It runs the same checks, then writes into the project the file that would be uploaded. Feature ids are plain names (`standoff`); two features of one package can't share one. The same project packed twice gives the same file. The [CLI reference](/docs/cli#fluidcad-pack) has every command and flag.

A package reaches other projects only through the hub. Until an admin approves it, try the package in its own project, with the test models at its root and the parts and assemblies in its folders. There is no step that installs your own file into another project.
